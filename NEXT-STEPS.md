## Settled on day 2: the backend design and stage 2

The backend design round is closed. See [ADR 0003](./docs/adr/0003-four-routes-with-short-polling.md) for the HTTP decisions and the options that lost.

The HTTP interface:

- Four routes for all seven Stages. Create a Project, record one Pick, ask for one Re-roll, read the Project.
- `201 Created` on create, and `202 Accepted` on a Pick and on a Re-roll.
- All four routes return the same Project document, so a caller learns one shape.
- One Pick route for every Stage, with `stage_number` as the discriminator and a body variant per Stage.
- Short polling on the one `GET` route every 3 seconds. No WebSockets and no long polling.
- One error shape on every route.

The database:

- A new `stage_run` table holds the state of a Stage that is working, broken, or done.
- Its `detail` column holds what a Stage has in hand before it finishes, for example the 10 proposed Topics and the counts the student already tried.
- A `running` row older than 5 minutes reads as failed, so a restart needs no sweeper.

Two new words are in `CONTEXT.md`. A Pick is the one item a student chooses from what a Stage offered. A Re-roll is a request for a new set instead. The Project entry no longer uses the word "run", so `stage_run` means what it says.

Stage 2 and the search:

- The search hands the rest of Fynd a list of Papers with the fields Fynd uses, and not the raw reply.
- A Paper keeps the Semantic Scholar identifier, the title, the abstract, the year, and the Open copy link. The arXiv identifier is dropped, because the first live run returned none. ADR 0007 adds the digital object identifier, because the second lookup needs that key.
- Every search reply and every model reply is cached in a file on disk. The cache key holds every value that changes the answer. See [ADR 0004](./docs/adr/0004-replayable-runs-and-versioned-prompts.md).
- A `429` or a timeout gets one retry after a short wait, then stops with a sentence that names the fix. A failed reply is never cached.
- Haiku 4.5 proposes the Topics, and Fynd asks for 10. A reply that does not match the shape gets one retry.
- The open Paper threshold moved from 5 to 3. A Topic under it costs the student nothing and does not spend the Re-roll. See [ADR 0002](./docs/adr/0002-topics-are-generated-then-verified.md).
- Stage 4 carries a guard for the lower threshold. When fewer than 2 Papers of a kept Topic give usable text, Fynd says so and offers the Topic list again.

## The scope change of 2026-10-07

A friend asked whether a chat assistant does all of this in an afternoon. The answer is that a chat assistant produces the output and never produces a guarantee, and the guarantee is the project. Research on what AI engineering interviews ask agreed with that and named the parts that carry weight: an evaluation harness with a golden set, retrieval scored on your own labelled data, faithfulness scoring, prompt versioning, and tracing with cost.

Fynd had one component with a number. It now has six. See the measured components table in `PRD.md`, and the revised three week plan for the days and the cuts.

Six items enter the plan, in this order.

1. Done as a decision. Prompts as versioned files, and a replayable cache. See [ADR 0004](./docs/adr/0004-replayable-runs-and-versioned-prompts.md).
2. Done as a decision. The tiered verifier, and a Claim stored as a located span. See [ADR 0005](./docs/adr/0005-a-claim-is-a-located-span.md).
3. The retrieval labelled set, hybrid search, and two embedding models compared. This closes the embedding decision by measurement. Note added 2026-10-20. One embedding model ships, published at two vector sizes, and the day 9 entry says why two could not resolve. The labelled set is now the Retrieval set.
4. Independence as a coauthor graph rule, with identifier deduplication.
5. Done as a decision, with item 2. Character offsets travel through extraction, normalization, and chunking, and the pipeline composes the offset maps.
6. Tracing with tokens, cost, and 95th percentile latency for each Stage.

Three cuts pay for them. Two Domains instead of three. Three standard cards at stage 3 instead of the bespoke picker. One buffer day instead of two. The Re-roll stays, because cutting it frees nothing.

The source for this change is `docs/architecture-review.md`, which is on disk and out of the repository.

## Settled on day 3: the shape of a Stage file

The first code design round is closed. See [ADR 0006](./docs/adr/0006-a-stage-offers-then-accepts.md).

- A Stage is two named jobs in one file. `offer` produces what the student chooses from, and `accept` refuses a Pick the Stage never offered.
- A Stage file knows nothing about HTTP, nothing about the command line, and nothing about Postgres.
- A Stage receives its search and its model as plain function arguments, with no default values. The edge wires the real ones.
- The runner is the one file that writes `stage_run` and `stage_state`, and the one file that knows the order of the seven Stages.
- `accept` checks the Pick against the offered list stored in `stage_run` `detail`, and never against a list the caller sent.
- `accept` returns what it decided, and does not raise for a normal outcome. Each answer is its own small class, so stage 1 returns `DomainKept` or `DomainNotOffered`, and stage 2 adds a third class for a Topic below the threshold.
- Tests pass fake search and model functions. The replay test over the committed cache arrives with the labelled set.

## Settled on day 3: the stage 3 logic

See [ADR 0008](./docs/adr/0008-stage-3-groups-claims-it-already-holds.md).

- Evidence first. Fynd gathers and verifies Claims, then groups them into 3 candidate Problems. The drafting call groups evidence and never invents a fact.
- The abstract is the Source text for a Paper at stage 3, because stage 4 fetches the Open copy later.
- A `source` row holds two texts with two hashes, and a `claim` row names which text its offsets belong to.
- The web search tool on the Anthropic API returns the links for a Statistic and a Product. Fynd fetches and extracts each page itself.
- The pool is 20 abstracts and at most 6 web pages, about 26 small calls, run one at a time and measured.
- Every verified Claim is stored. The link table joins only the Claims a candidate Problem uses.
- A Paper that OpenAlex marks as retracted is dropped, and the drop is counted.
- The Evidence window is 5 years, and it applies to a Claim that proves the Problem is real. An Existing approach and the Technical core carry no window.
- Stage 2 and stage 3 search with the year range. Stage 5 searches again with no range.
- Too little evidence shows fewer cards with a sentence that says why. An empty pool returns the student to stage 2.
- A Re-roll names the 3 rejected statements and regroups the same cached pool.

## Settled on day 4: the Open copy pipeline

The design round for step 3 is closed. Four rounds of questions, and the answers are below. Nine issues hold the work, numbered 5 to 13 on GitHub, with the blocking edges set.

The pipeline:

- One fixed pool. The Seeded Topic query is `United Kingdom household energy forecasting`, the limit is 20, and the Evidence window applies. The day 1 pool in ADR 0007 carried no window, and the measurement file says why its numbers differ.
- A Paper with a digital object identifier goes to OpenAlex. Fynd takes the best open location unless it is the publisher, and then the first repository location. A Paper with no identifier or no record falls back to the Semantic Scholar link.
- The fetch rules are the rules in ADR 0007. `FYND_CONTACT_EMAIL` has no default, because a hard coded address in a public repository is a scraped address.
- pdfplumber returns the text plus the page spans. trafilatura returns the text with an empty structure. A section finder is the handover's problem, and nothing before it reads a section label.
- Usable text starts at 3,000 characters and 80 percent letters and ordinary punctuation. The section word check waits for the first measurement, because a threshold tuned on no data drops a good file in silence.
- One result class holds the location, the text, and a reason from eight fixed strings. Eight classes buy nothing, because the only reader is a table that counts reasons.
- Step 3 ends at the Source text. Normalization, dehyphenation, and chunking arrive in step 4, against a real chunk size and a real prompt.

The cache and git:

- The cache holds bytes in a sidecar file beside the JSON file that holds the parts. A 20 megabyte file is not a JSON value.
- A refusal is cached with its status and its content type, because the measurement counts the hosts that return no file. A timeout and a 429 are never cached.
- Three keys. OpenAlex keys on the identifier. The fetch keys on the link with its limits. The extraction keys on the hash of the bytes with the extractor name and version. A new library version then misses the extraction cache and hits the fetch cache.
- Git holds the extracted texts, the OpenAlex answers, and the refusals. Git holds neither the fetched bytes nor the Semantic Scholar replies. See [ADR 0011](./docs/adr/0011-the-public-repository-holds-the-text-and-not-the-files.md).
- The labelled set of 10 Sources comes from Sources with an open license, because that text is the text continuous integration replays.

The files, and one correction:

- `openalex.py` and `fetcher.py` take an `httpx.Client`, as `semantic_scholar.py` does. `open_copy.py` joins resolve, fetch, extract, and check, and takes all four as plain function arguments. Stage 4 calls that file, and its test performs no HTTP.
- `extract.py` holds the two extractors, and `source_text.py` holds the checks.
- ADR 0007 said an extractor returns an offset map. ADR 0005 says an offset cannot point into PDF bytes. ADR 0005 wins, and ADR 0007 carries a dated note.

Usable text is now its own entry in `CONTEXT.md`, because three code paths read it.

The one open item is a number and not a preference. The two thresholds and the section word check are set by the first measurement, which is issue 13.

## Settled on day 8: how stage 2 asks for a Topic, and three outside references

Updated 2026-10-19. No code changed today. This entry answers one question and records three repositories read on 2026-10-19.

### How the model proposes a Topic

Yes, there is a prompt, and it is the only prompt file that exists. It is `prompts/propose-topics-v1.md`, and it holds 23 lines. ADR 0004 names three prompts. The Claim extraction prompt and the drafting prompt are not written.

The prompt holds four placeholders. `{{TOPIC_COUNT}}` is 10. `{{DOMAIN_NAME}}` is the Domain the student kept at stage 1. `{{AVOID_LIST}}` names the Topics a Re-roll already showed, and reads `none` on a first ask. `{{RETRY_NOTE}}` is empty on the first ask.

The prompt states four rules for a Topic.

- The Topic names a real area of work, and not a product idea.
- Published research exists, so a search returns papers from the last five years.
- One student builds software about the Topic in one academic year.
- The Topic is narrow enough to search, and wide enough to hold several papers.

Each Topic carries two fields, and the difference matters. `label` is what the student reads, in five words or fewer. `query` is what Fynd sends to Semantic Scholar, in three to eight words, with no punctuation and no boolean operators.

`offer_topics` in `src/fynd/stages/stage2.py` asks for 10 Topics and shows 5 to 8. The extra two cover the items the shape check drops. The answer shape is a JSON schema that lives in the Stage and not in the model client. The shape of an answer is a rule of the Stage.

Two facts about the prompt file are load bearing.

The whole file content is hashed, and the hash is part of the cache key. A typo fixed without a rename still misses the cache. So no published number belongs to a prompt that nobody can read.

The retry note is the second ask, and it is only filled on attempt 2. The model runs at temperature zero, and the cache keys on the filled text. An identical second ask returns the first unusable answer off disk for ever. The note changes the text, which changes the hash, which makes the retry a real second question.

### The finding that matters for the search

No code tests the `query` field against its own rules. The prompt asks for three to eight words with no boolean operators. Neither the JSON schema nor `topics_from_answer` enforces either rule. The query reaches Semantic Scholar as the model wrote it.

This is the cause of a number already in this file. 2 of the 20 Papers of the measured pool are about ultra-processed food. The search is not precise, and the query is unmeasured. The retrieval labelled set is where that becomes a number.

### Designed on day 8 for release 2: the free text search bar

A student types a sentence into a search bar instead of picking from the list. `PRD.md` holds this as a non-goal for version 1, at the lines about free text Topic entry and about a chat interface. This entry is the design, and it is not permission to build.

The rule that keeps ADR 0006 intact: free text is a way into the offered list and never a replacement for the Pick. `accept_domain` and `accept_topic` still receive a Pick that Fynd offered.

The branch the student asked about mostly disappears, for two reasons.

The 26 OpenAlex fields cover all of published research. No sentence a student types lands outside them, so a Domain router always lands somewhere. The worst case is an odd fit and not a miss.

What a student types is almost never a Domain. "Reducing food waste in restaurants" is a Topic. Fynd already holds the machine that tests an arbitrary Topic. The search plus `count_papers_with_a_candidate` takes any query string and answers whether recent, fetchable, open literature exists for it. That is the internet search, and it is written, cached and measured. So the free text path reuses the gate and needs no new verifier.

The path, end to end.

1. The student types a sentence.
2. The model returns a `label` and a `query`, which is the job it already does at stage 2.
3. The existing search runs with the Evidence window.
4. The existing gate counts the Papers with a candidate.
5. 3 or more Papers means the Topic proceeds.
6. Fewer means Fynd shows the count and offers the Domain list, as a weak generated Topic does today.

Three costs to plan for.

A free text Topic skips the feasibility rule. The prompt makes the model promise that one student builds the Topic in one academic year. A typed sentence carries no such promise, and "build artificial general intelligence" passes the literature gate easily. So free text needs one extra closed question about buildability. The Roam repository in [docs/references.md](./docs/references.md) shows the shape. The model picks from a fixed set of answers with a probability, and the code owns the threshold.

Free text is the first untrusted student writing to enter Fynd. Today the only input is a Pick from a closed list, so nothing can be injected. Once a sentence reaches a prompt, prompt injection is real. Roam trims to 300 characters, drops control characters, escapes before the query, and tests an injection attempt.

Voice input is a separate and larger cost, and it is not part of this design. It needs speech to text, a microphone permission, and a text alternative for metric 4. Text first.

Recall at 20 only sees the line between 0 and relevant, so the two passes agree exactly on the number the table publishes. 19 of the remaining disagreements were a 1 against a 2, which only nDCG sees, and every one of them was a household forecasting paper that the restated rule makes a 2.

Four earlier guesses about the disagreement were tested and all four were wrong. The country was not inflating the hand grades, because both graders scored the United Kingdom papers lower. The 8 Papers with no abstract did not move the hand grades at all, at 0.88 against 0.85. The model pass was the biased one there, reading household-sounding titles optimistically with no abstract to check them.

### Why a strict gate, and not a generous one

A pool where 51 of 60 Papers count as relevant leaves recall at 20 unable to tell a good ranking from a random one. At 39 of 60 it can. So the gate is strict on purpose, and a national or city or grid forecast is a 0 even when it is a good paper.

### What enters git

The graded set file, with no abstract and no year. Beside it, three grader passes, each stamped with the hash of the rule that produced it: the hand pass and the model pass under the final rule, and the two title-only passes kept as evidence of how much the abstract matters. No published number is scored against a model pass.

### The limits the table has to state

One person's judgement decides every published grade, because Fynd is a solo project. A second pass exists and it is a model, not a second person.

Recall over a pool is recall inside the pool. A relevant Paper that none of the four queries returned is invisible to every number in the table.

No number says anything about whether Fynd finds United Kingdom evidence, because the grade ignores the country by design.

## Published on day 11: the retrieval table, and a baseline the design did not plan

[docs/measurements/retrieval-table-2026-10-20.md](./docs/measurements/retrieval-table-2026-10-20.md) holds the first retrieval number of this project. Issue 34 is done. `uv run python -m fynd.cli measure-retrieval --as-of 2026-10-20` writes it, and the file is named after the graded set and not after the day, because the set decides every number in it.

Two decisions of the day 9 design changed, and both are recorded here.

### The baseline is the four searches interleaved

The day 9 design made the baseline the ranking of the `query` the model wrote. That query is gone, because the model never proposes the Seeded Topic, which is the day 10 finding and now issue 43. So the baseline is the order the four searches really arrived in, taken one rank at a time from each query. The set builder already pools them in that order, so the baseline row is built by shipped code and not by a second rule written for the table.

The other three readings were refused. A pool of 15 Papers makes recall at 20 equal 100 percent for every row, so the headline number would say nothing. Ranking each query's 50 returned Papers holds all 15 graded Papers inside the first 20 of the arriving order, so the baseline would read 100 percent again.

### nDCG gives a Paper its grade as the gain

A 2 is worth twice a 1. That is the original linear form, and it is the default of the scikit-learn function, so a reader can reproduce the number. The other published form weighs a 2 three times a 1. The file states which one it used, because nothing here is tuned and a reader cannot tell the two apart from a number.

### What the numbers say

The baseline reaches 17 of the 39 relevant Papers inside the top 20, which is 44 percent. The four query rows are the day 8 finding about an untested query, and the spread is wide: the `wider` query reaches 14 of 39, the `hand` query 8, and the `reworded` query 4. One query returned 15 Papers of the pool, so a query row cannot fill 20 places and the query rows compare with each other and never with the baseline.

No row is a ranking of Fynd yet, and the file says so in a sentence that disappears by itself when the first one arrives. Issues 35, 36 and 37 add the BM25 row, the two meaning rows, the fusion and the reordered fusion. The code for all of them is in `src/fynd/retrieval.py` already, with the match reason, so those tickets wire rows and publish numbers.

## Measured on day 12: BM25 ranks worse than the order the search returned

Issue 35 is done, and the BM25 row is in [docs/measurements/retrieval-table-2026-10-20.md](./docs/measurements/retrieval-table-2026-10-20.md). It reaches 12 of the 39 relevant Papers inside the top 20, which is 31 percent. The baseline reaches 17, which is 44 percent. nDCG at 10 says the same, at 0.561 against 0.897. 26 of the 32 Papers graded 2 sit outside the top 20.

A row that loses to the arriving order is a finding and not a failure. Two causes were on the table, and one measurement separated them.

### The first guess was the missing abstracts, and it is the smaller cause

8 Papers of the 60 carry no abstract, and 6 of those are graded 2. They sit at places 23, 24, 25, 40, 59 and 60, which looks damning until you notice that the list is every graded 2 with no abstract and not a sample of anything.

The missing text cuts both ways. A title is a short document, and BM25 divides a score by the length of the document, so a 22 word title that holds four query words outranks a 250 word abstract that holds five. The Paper at place 1 of the BM25 row has no abstract.

Ranking only the 52 Papers that do have an abstract settles it. BM25 reaches 11 of the 31 relevant Papers there and the arriving order reaches 13. So BM25 still loses with every abstract present, and the missing text is not what decides the row.

### The real cause is that the query names a country and the grade ignores it

The Topic is "United Kingdom household energy forecasting", so the query carries five stems and two of them name a place. The grading rule throws the place away on purpose, because `CONTEXT.md` gives the place to a Statistic, and the day 10 entry records why a Spanish household forecasting Paper is a 2.

So the two disagree, and the word counter follows the words. An ultra-processed food Paper graded 0 sits at place 10, because its abstract names United Kingdom households and energy. Four Papers about United Kingdom energy policy and energy use outrank Papers that forecast household demand without naming the country.

The same BM25 over the same pool, asked for "household energy forecasting", reaches 20 of 39 and scores 0.945. That number is a diagnosis and it is not in the table, because a query chosen after seeing its score fits the set, which is the one thing the file promises it did not do. A query rewriting rule has to be decided first and measured after, on a set that was not used to find the effect.

### One more thing the diagnosis turned up

`stem("united")` returns `unit`, because the rule strips a trailing "ed". 28 of the 60 Papers hold `unit` and only 23 hold `kingdom`, and the matches include a Paper about the United States and a Paper about Nigeria. So one of the two country stems is a collision, and the `ponytail:` comment in `src/fynd/retrieval.py` already names that ceiling. A Porter stemmer would remove it, and nothing here says yet whether it would move a published number.

### The fix: a Topic has a label and a query

A `Topic` has carried a `label` and a `query` as separate fields since ADR 0002, and nothing had ever used the difference. The Seeded Topic was one string, so a ranking had nothing else to ask for.

Now it is two. The label names the place and a student reads it, because the Problem belongs to a place and a Statistic proves it. The query names the subject and the search and every ranking read it, because a method a student copies does not change at a border. See [ADR 0015](./docs/adr/0015-a-topic-has-a-label-for-the-student-and-a-query-for-the-search.md) and the entry in `bugs.md`.

The table holds a row for each string, and the gap is the finding. BM25 asked for the label reaches 12 of 39 at an nDCG of 0.561. BM25 asked for the query reaches 20 of 39 at 0.945, and both numbers beat the arriving order at 17 of 39 and 0.897. Recall at 10 reaches 10 of 39, which is every place the cut allows.

Both rows stay. A table that showed only the better one is a configuration chosen after the numbers, and the order of events is written down: the diagnosis came first, and the decision rests on `CONTEXT.md` and not on the score.

A country filter was considered and refused. Semantic Scholar gives a Paper no country field, so a filter is the same word match again, and the grading rule calls a Spanish household forecasting Paper a 2. The supervisors ask for the last 5 years, a citation count, and relevance, and the Evidence window already covers the first.

### One thing the citation count turned up

`citationCount` is not in the fields Fynd asks Semantic Scholar for, so no Stage and no card can show it. That is a bonus and not a blocker, and it has no issue yet.

## Measured on day 13: meaning beats the arriving order, and the place stops hurting

Issue 36 is done. Four meaning rows are in [docs/measurements/retrieval-table-2026-10-20.md](./docs/measurements/retrieval-table-2026-10-20.md), one for each vector size and one for each string of the Topic.

| Row | Recall at 20 | nDCG at 10 |
|---|---|---|
| Baseline | 17 of 39 | 0.897 |
| BM25, label | 12 of 39 | 0.561 |
| BM25, query | 20 of 39 | 0.945 |
| Meaning 1024, label | 18 of 39 | 0.780 |
| Meaning 1024, query | 18 of 39 | 1.000 |
| Meaning 512, label | 18 of 39 | 0.780 |
| Meaning 512, query | 17 of 39 | 1.000 |

### A vector carries the place and a word counter trips over it

This is the question day 12 left open. BM25 lost 8 Papers when the search asked for the label and not the query, at 12 against 20. The meaning ranking loses nothing. It reaches 18 Papers for both strings at 1024, and at 512 the label row reaches 18 and the query row 17, so the place costs the meaning rows no Paper at either size.

So the two kinds of ranking fail differently on the same string. A word counter treats "united" and "kingdom" as two more words to count, and the grading rule throws the place away, so every Paper that merely names the country rises. A vector reads the whole phrase, and a Paper about household energy forecasting in Spain still sits near it. The label costs the meaning rows their ordering and not their reach, which is the 0.780 against 1.000 at nDCG.

ADR 0015 stands either way, because a ranking reads the query and a student reads the label. The finding is that the dense row is the forgiving one when the label leaks into a search.

### The top 10 of the query rows is a perfect order

Both query rows score 1.000 at nDCG 10, which means no order of this pool puts better Papers in those 10 places. Recall at 10 reaches 10 of 39, which is every place the cut allows.

That number is smaller than it looks. nDCG at 10 compares against the best 10 Papers of the pool, and the pool holds 32 Papers graded 2, so filling 10 places with 2s is enough to score 1.000. It says the first 10 Papers are all the best grade, and it says nothing about place 11 onward.

### 512 costs one Paper of 39, and only on one of the two rows

The query row reaches 18 Papers at 1024 and 17 at 512. The label row reaches 18 at both. So the half size costs one Paper of 39 on one row of two, and the ordering inside the top 10 does not move at all.

That is the measured case for a 512 column, which halves what a Paper costs to store. The number is one Paper on one set and on one row, so the decision is a measured preference and not a settled fact, and the second embedding row of a later set can overturn it.

### The model changed, because the free tier refuses the series 4 model

The first live run of the embedding client failed. `voyage-4-lite` is refused with a 429 whose message names a missing payment method, and the refusal arrives for a request of one token, so it is a plan limit and not a rate limit. The same key answers 200 for `voyage-3.5-lite`, and the 200 million free tokens are a series 3 offer.

Fynd now embeds with `voyage-3.5-lite`. The account stays prepaid, which is the rule the technical direction table set, and every row of the table prints the model name beside its size.

### The client paces itself, because the free tier is 3 requests and 10000 tokens a minute

A pool of 60 abstracts is about 18000 tokens, so one request for the whole pool breaks the token cap. A table of two sizes and two strings is more than 3 requests, so it breaks the request cap too.

The client now cuts a pool into slices of about 3000 tokens, and it waits 21 seconds between requests. 3 requests a minute at 3000 tokens is 9000 a minute, which holds both caps at once. The whole table cost 16385 tokens, and a second run costs nothing, because every vector is on disk.
