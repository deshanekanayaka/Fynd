# The real world supplies the Problem, the literature supplies the evidence

Fynd first worked the other way around: read papers, find a research gap, propose a proof of concept. That shape produced proposals a bachelor's student cannot build, because a research gap in a studied field asks for a research contribution. We inverted it. A Problem is now a real situation, often a United Kingdom business problem, and Sources exist to prove the Problem is real, to show the Existing approaches, and to supply the Technical core the student implements. A Problem that already has solutions is acceptable, because the student's contribution is a different solution and not a new finding.

## Consequences

The evidence bar is 3 or more Claims from independent Sources, with at least one Paper and at least one Statistic or Product. Papers alone are not enough, because three papers and no sign that anyone outside a university cares is the exact failure this decision prevents.

A Source is therefore not only a Paper. An official statistic proves the Problem, and a commercial Product proves demand and sets the bar a Proposal must clear. The retrieval pipeline, the glossary, and the labelled evaluation set all follow from this, so a later return to literature-first work would rewrite all three.

Every Proposal must name a Technical core and cite the Source it comes from. This is the answer to a supervisor who says an idea lacks technical depth. Without the rule, Fynd returns the CRUD application the student would have proposed alone.

## Considered options

Literature first, as originally written. Rejected because it produces proposals above the level of the user, and because it hides the real-world justification a supervisor asks for first.

The student brings the Problem and Fynd only researches it. Rejected because choosing the Problem is the step students find hardest, so removing it removes most of the value.
