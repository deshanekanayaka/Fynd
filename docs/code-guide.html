The code in three connected flows

The project begins with a Domain and narrows to a Topic. Separate commands already fetch and read Papers and measure retrieval. These pieces are not yet a complete seven-Stage application.

01 · Offer a Topic

Stage 1 → Prompt → Claude → Stage 2

The AI proposes Topics; Python checks the Pick using real literature.

02 · Read a Paper

OpenAlex → Fetcher → Extraction → Text checks

A file candidate becomes Source text only after downloading and extraction.

03 · Measure a ranking

Retrieval set → Grades → Ranking → Report

The same graded pool compares keyword and meaning-based rankings.

Defines the Topics, Papers, search responses, and Open copy locations that other files exchange.

src/fynd/models.py ↗

Why this file exists

The search client receives a large API reply, but ranking needs only a Paper’s title, abstract, and identifier. Shared types give both files the same named fields, instead of making each one interpret raw JSON.

The flow

  1. API or model reply

    Outside services return JSON.

  2. Named values

    Clients and Stage 2 create Pydantic models.

  3. Stage or ranking

    Other code reads fields such as paper.title.

A small example

Field(default_factory=list) gives each SearchResult its own empty list. Missing metadata uses defaults such as an empty abstract or year=None.

cache.py

Saves external answers and downloaded files on disk so Fynd can reuse work it has already done.

src/fynd/cache.py ↗

Why this file exists

Without the cache, running the same Topic again could repeat searches, download the same PDFs, and pay the AI model again. A cache lets the caller reuse an answer, reducing repeated requests, cost, and waiting. It also lets checks replay recorded answers.

The flow

  1. Build a key

    Identify the request by the inputs that affect its answer.

  2. Look on disk

    A usable entry is a cache hit: reuse it.

  3. Do missing work

    On a miss, the caller requests or computes an answer and stores it.

A small example

What is actually stored?

Work Cached answer
Paper search Titles, abstracts, identifiers, and metadata
AI request Generated structured answers
Embedding A list of numbers for one text
Download Bytes in a .bin file, with JSON metadata beside it
Extraction Source text, extractor version, and display spans
Fetch refusal Status, content type, and reason

The caller decides what is safe to cache. The cache does not make requests itself, and its general JSON writer does not validate a service’s answer.

The pieces inside

Name What it does
CachedBytes A downloaded byte sequence and its content type, such as application/pdf.
cache_dir Finds or creates the cache directory. FYND_CACHE_DIR overrides the default .cache.
cache_key Hashes request details into a filename such as claude-<hash>.json.
read_file Reads JSON; missing files and malformed JSON return None.
read / write Loads a stored value or saves it alongside its identifying inputs.
bytes_path Finds the .bin companion file for an entry.
read_bytes / write_bytes Loads or stores file bytes separately from JSON metadata. Reads check the byte count.
write_refusal / is_refusal Stores and recognises fetch refusals. HTTP 429 is rejected because a rate limit is temporary.
sha256_of Hashes bytes, for example to identify the input to extraction.
read_parts Returns the recorded inputs so a reader can trace an answer.
Keep in mind

The JSON example omits some real key fields for readability. Writes are not atomic, file size is not a full integrity check, and local disk survival after deployment restarts is not yet designed. Only available replay data can be reused.

prompts.py

Loads a saved prompt, hashes its wording, and fills its placeholders before an AI request.

src/fynd/prompts.py ↗

Why this file exists

A prompt edit can change the answer. Hashing the whole file makes that edit part of the cache identity, even when the filename stays the same.

A prompt is saved text containing instructions for the AI. Stage 2 currently loads prompts/propose-topics-v1.md, which asks Claude to propose Topics. This module only prepares that text; claude.py sends the request.

The flow

  1. Load

    Read prompts/<name>.md, keeping the original text and its hash.

  2. Fill

    Replace placeholders with values such as the Domain.

  3. Send

    Stage 2 passes the filled prompt and original file hash to the model client.

A small example

The original Prompt stays unchanged. fill returns a new string; it does not edit the file or call the AI.

Why are there two hashes?

The hash stored in Prompt.sha256 identifies the original file wording. The Claude client separately hashes the filled text, so using Energy instead of Technology also creates a different cache entry.

What happens if a placeholder is wrong?

If the file contains {{DOMAIN_NAME}} but the supplied dictionary uses DOMAIN, fill raises KeyError rather than replacing part of the name. It also raises if a placeholder is left unfilled. Repeated occurrences of the same placeholder are all replaced.

The pieces inside

Name What it does
Prompt The filename stem, original text, and SHA-256 hash.
prompts_dir Uses FYND_PROMPTS_DIR when set; otherwise finds the repository’s prompts directory.
load Reads the named .md file and hashes its complete text.
fill Replaces exact {{PLACEHOLDER}} strings and rejects missing or leftover placeholders.

Prompt is a frozen dataclass: its fields cannot be reassigned after creation. name is the filename without .md, text is the unfilled wording, and sha256 is its 64-character hash. The directory defaults to the repository's prompts/ folder; FYND_PROMPTS_DIR can point tests at temporary files. A missing prompt file raises FileNotFoundError.

Keep in mind

Only propose-topics-v1.md currently exists. Claim extraction and Proposal drafting prompts are planned work.

contact.py

Builds the operator contact details used by OpenAlex and file-fetching requests.

src/fynd/contact.py ↗

Why this file exists

A host receiving automated downloads should be able to identify Fynd and contact its operator. Reading the address from the environment keeps a personal address out of source code.

The operator is the person running Fynd. OpenAlex uses this file for its mailto query parameter and User-Agent header. The file downloader uses the same User-Agent when requesting robots.txt and PDF files. Claude, Voyage, and Semantic Scholar do not use these helpers in the current code.

The flow

  1. Environment

    FYND_CONTACT_EMAIL supplies the operator address.

  2. Contact string

    Read and check that it is present.

  3. Request header

    Build a User-Agent naming Fynd and its repository.

A small example

A User-Agent is an HTTP header identifying the program making a request. Here it names Fynd, links to the repository, and provides the operator's email address.

Where does the address come from?

The CLI loads .env into the process environment. contact.py reads the environment variable; it does not open .env itself. contact_email removes leading and trailing whitespace, then raises ContactEmailMissing if the result is empty. It checks presence, not whether the address is correctly formatted or can receive mail.

There is no default address: the person running Fynd must supply one. The existing .gitignore keeps .env out of the repository.

The pieces inside

Name What it does
ContactEmailMissing Raised when FYND_CONTACT_EMAIL is missing or blank.
contact_email Returns the configured address; it checks presence, not email syntax.
user_agent Builds the identification string used by OpenAlex and the fetcher.

stage2.py

Asks an AI model for Topics, then checks whether a picked Topic has enough recent Papers with candidate files.

src/fynd/stages/stage2.py ↗

Why this file exists

A Topic that sounds interesting may have too little accessible literature. The AI proposes the list; a real search and OpenAlex lookup check the student’s Pick.

The flow

  1. Propose

    Ask for 10 Topics; keep 5–8 usable entries.

  2. Pick

    The student sends an offered Topic’s slug.

  3. Check

    Search recent Papers and require at least 3 with OpenAlex file candidates.

A small example

A retry repairs an unusable model answer. A Re-roll asks for a new list after the student rejects the previous one; the previous labels go into the avoidance field. Product rules allow one Re-roll, but the current CLI has no persisted counter to enforce it.

What gets checked before a Topic is offered?

The model is asked for 10 entries. topics_from_answer skips entries without usable label/query fields, creates an ASCII slug from the label, and removes duplicate slugs. At least five surviving entries are required, and at most eight are returned.

If too few survive, a retry note changes the second filled prompt and its cache key. Two undersized lists raise TopicListUnusable. That retry applies to list processing; model-client exceptions propagate instead of entering this list-retry path. Prompt rules such as query word count and the label's place wording still need their planned enforcement work.

What happens after the student picks?

accept_topic requires the Pick's slug to match an offered Topic. An unoffered slug is refused before any search. For a valid Pick, it searches with the Topic's subject query and the five-calendar-year Evidence window: in 2026, the first accepted year is 2022.

Each Paper with a DOI is looked up through the supplied resolver. A non-empty OpenAlex candidate list adds one to the Paper count, even if that Paper offers several locations. Papers without a DOI or whose lookup raises WorkNotRead add nothing. Transport and timeout exceptions are not caught by this helper.

At least three qualifying Papers returns TopicKept; fewer returns TopicBelowThreshold with the count, so the caller can keep the offered list available. A below-threshold Topic is a normal decision, not a broken Stage. No file is downloaded and no Claim is extracted here.

Why is this separate from the CLI?

The Stage owns the Topic acceptance rule. The CLI supplies real service functions, and tests supply fakes. The future runner must use saved offered Topics and enforce saved Re-roll limits; the current command-line path reconstructs offers from the prompt cache and holds no Project state.

The pieces inside

Name What it does
AskModel / Search Interfaces for the model and search functions supplied by the caller.
TopicKept / TopicBelowThreshold / TopicNotOffered Separate outcomes for an accepted Topic, insufficient file candidates, or an unoffered Pick.
TopicListUnusable Raised when two model answers both produce fewer than five usable Topics.
first_year_in_window Starts the five-calendar-year Evidence window: in 2026, this returns 2022.
slugify Turns a label into lowercase ASCII letters, digits, and hyphens.
topics_from_answer Drops empty entries and duplicate slugs, then builds Topic values.
offer_topics Fills the prompt, calls the supplied model, and allows one retry for an unusable list.
count_papers_with_a_candidate Counts Papers whose DOI resolves to at least one OpenAlex candidate. It downloads no files.
accept_topic Checks the slug, runs the search, and compares the candidate count with the threshold of 3.
Keep in mind

Current wiring searches 20 Papers and has no ranking cut. Searching 50 and ranking down to 20 is planned under issue #39. The prompt does not yet enforce ADR 0015’s place/subject distinction; query-rule work is recorded under #38.

claude.py

Sends a filled prompt to Claude and returns a structured JSON answer, reusing cached answers when available.

src/fynd/claude.py ↗

Why this file exists

Stage 2 decides what Topics should look like. This file handles the service request, response parsing, and caching, so the Stage can be tested with a fake model function.

The actual instructions come from prompts.py; the expected JSON fields come from Stage 2. This client sends both to Claude. The SDK reads ANTHROPIC_API_KEY from the environment when a live request is needed.

The flow

  1. Check cache

    Use model, prompt hash, input hash, token limit, and schema version.

  2. Ask Claude

    Request the Stage’s JSON schema with claude-haiku-4-5 by default.

  3. Read answer

    Reject refused, truncated, missing, or non-JSON text before caching it.

A small example

What does the schema do?

The schema describes the expected fields and types. For Topic generation, it asks for a topics list whose entries contain label and query strings. It controls response structure, not whether an offered Topic is useful or has enough literature.

What identifies a cached answer?

The model identifier, original prompt hash, filled-input hash, reply-token limit, and schema version all contribute to the key. For example, changing the Domain changes the filled text and produces another key. Changing the response schema requires the caller to bump its version; the schema itself is not hashed here.

What happens to a broken answer?

The client rejects explicit refusals, answers stopped by the token limit, missing text, and text that cannot be parsed as JSON. These answers are not cached. It reads the first text block and uses json.loads to turn it into a Python value.

The client does not separately validate the parsed value against the schema. Stage 2 still filters unusable Topic entries and can retry a list with too few usable Topics. SDK or connection errors propagate to the CLI's error handler.

What are the 4,000 tokens for?

MAX_TOKENS limits the length of the generated reply. Tokens are pieces of text rather than a fixed number of words. This setting does not cap the whole Project's API spending.

The pieces inside

Name What it does
HAIKU / MAX_TOKENS The default model identifier and the 4,000-token response limit.
ModelRefused Raised when the response cannot be used as JSON or stops early.
ask_for_json Reads a cached answer or sends the request, parses its text, and saves the result.
Keep in mind

No temperature or other decoding parameter is sent. A fresh model call may differ; repeatability comes from replaying the saved answer. JSON shape alone does not prove that a Topic meets the product rules.

semantic_scholar.py

Searches Semantic Scholar for Papers and converts the reply into Fynd’s Paper and SearchResult types.

src/fynd/semantic_scholar.py ↗

Why this file exists

Fynd needs actual academic records behind a Topic. Keeping API details here means Stage 2 can ask for Papers without knowing endpoint URLs, headers, or response field names.

This is a metadata search, not a PDF download. It returns the title, abstract, year, identifiers, and reported open link; OpenAlex and the fetching pipeline handle locating and reading files later.

The flow

  1. Search words

    Receive a query, first accepted year, and result limit.

  2. Service or cache

    Reuse an answer, or make a paced API request.

  3. Papers

    Return named Paper values inside a SearchResult.

A small example

What does a search ask for?

The caller calculates the Evidence window. This client only passes the supplied year range to the service. SearchResult.total is the service's reported match count; len(result.papers) is how many Papers this response actually contains. A total of 800 with a limit of 20 does not mean Fynd downloaded or read 800 Papers.

When does it make a request?

The query, result limit, year filter, requested fields, and reply-shape version identify the cache entry. An identical search can reuse its stored reply. Changing the limit from 20 to 50 creates a different entry because the requested answer has changed.

On a cache miss, this client waits until at least one second has passed since its last response. That timing belongs to this client instance; separate instances do not share a rate limiter. The request includes SEMANTIC_SCHOLAR_API_KEY when it is set.

What happens when a request fails?

HTTP 429 means the service is rate limiting the request. The client waits three seconds and tries once more; a second 429 raises RateLimited. Other HTTP errors and connection or timeout errors propagate without this retry. No failed request is written to the search cache.

Why read abstracts from the cache?

Human grading needs Paper abstracts, while ADR 0011 keeps the search replies containing them out of the public repository. cached_abstracts reads the available local search entries and returns a dictionary keyed by Paper identifier. Entries without an identifier or abstract are left out, so the grading command can say the abstract is missing. This function makes no network request.

The pieces inside

Name What it does
RateLimited Raised after two HTTP 429 responses.
paper_from_api Maps API names and missing values into a Paper.
SemanticScholar Keeps an HTTP client, API key, and last-request time.
wait_for_rate_limit Leaves at least one second between this client’s requests.
search Caches by query, limit, year range, requested fields, and shape version.
fetch_search Calls the endpoint and retries a 429 once after a wait.
cached_abstracts Collects abstracts from locally cached search replies for human grading.
Keep in mind

The search method defaults to 20 results; the Retrieval set builder explicitly requests 50. A reported open link is metadata, not proof of a downloadable file.

openalex.py

Looks up a Paper by DOI and returns up to three candidate Open copy file locations.

src/fynd/openalex.py ↗

Why this file exists

A Semantic Scholar link can lead to a landing page rather than a file. OpenAlex supplies additional open locations, letting Fynd try repository files before other hosts.

A DOI is a digital object identifier for an academic work, such as the illustrative 10.1000/example. It identifies the Paper rather than naming a particular PDF file. OpenAlex uses that identifier to find metadata describing where copies may be available.

The flow

  1. DOI

    Receive the Paper’s digital object identifier.

  2. Open locations

    Read the cached or live OpenAlex record and filter its locations.

  3. Candidates

    Return repository-first candidates, or a reason there are none.

A small example

How are candidate files picked?

  1. Keep locations marked open.

    Start with OpenAlex's preferred open location, then inspect its other locations. Repeated locations are removed.

  2. Require a PDF link.

    A landing page alone is not enough. Links on the configured non-file hosts doi.org, dx.doi.org, and doaj.org are excluded.

  3. Order and cap the list.

    Repository locations come first, followed by other host types. Their original order within each group stays intact. Return at most three candidates.

An explicit licence string is retained when available, but it is not required: the qualifying field is OpenAlex's is_oa mark. A candidate may still fail when the downloader tries it.

What does a lookup return?

Situation Result
A record with eligible file locations found=True, a candidate tuple, and an empty reason
A record with no eligible file locations found=True, no candidates, and a reason such as no_pdf_link
HTTP 404: no matching record found=False and no_openalex_record
Another HTTP status, such as 429 or 500 WorkNotRead; nothing is cached

HTTP 200 records and confirmed 404 answers are cached. The filtering rules run on that saved metadata again each time, so changing the candidate rules does not require another external lookup. Cached records have no automatic refresh in this client.

What happens on a live request?

The request includes the operator's contact email and a User-Agent identifying Fynd. The default HTTP client has a 30-second timeout. Unlike the Semantic Scholar client, this client has no explicit pacing or retry loop; timeout and connection exceptions propagate. Lookup success does not prove a file can be downloaded or that its text will pass the quality checks.

The pieces inside

Name What it does
Resolution Whether the DOI was found, its candidate locations, and a reason if none qualify.
WorkNotRead / Resolve The lookup failure and the callable interface used by Stage 2 and the pipeline.
host_of / is_repository Reads a URL’s host and checks a location’s repository type.
holds_no_file Checks the configured doi.org, dx.doi.org, and doaj.org blocklist.
open_locations Collects locations marked open and removes repeated locations.
open_candidates Keeps PDF links outside the blocklist, ranks repositories first, and caps at 3.
reason_for_no_candidate Distinguishes no open location, no PDF link, and blocklisted-only candidates.
OpenAlex.resolve Reads or caches the lookup and converts it into a Resolution.
OpenAlex.fetch_work Requests the DOI record. A 404 is cached as not found; other non-200 replies raise.
Keep in mind

A candidate is a location to try, not a guaranteed download. The current resolver does not expose or enforce the planned retraction check.

voyage.py

Gets text embeddings and reranking scores from hosted Voyage models, with caching and request pacing.

src/fynd/voyage.py ↗

Why this file exists

Keyword matching misses related wording. Embeddings help compare meaning; reranking considers a query alongside each document. Saving individual embeddings avoids paying again for overlapping Paper lists.

The flow

  1. Texts

    Receive the query or Paper titles and abstracts.

  2. Missing work

    Load cached vectors; group uncached texts into estimated token batches.

  3. Vectors or scores

    Call the hosted model and return the results in usable order.

A small example

Why cache one vector per text?

The cache identity includes the text, embedding model, query/document mode, dimensions, and request-shape version. Changing any of those settings produces a different entry. Duplicate uncached text is sent once; the returned list restores its original positions. Entirely cached or empty inputs make no request, so no live API key is needed by this client for those paths.

What is a slice?

It is a batch of texts sent in one embedding request. estimated_tokens uses len(text) // 4 + 1, and slices groups texts around a 3,000-estimated-token budget. This is a character-based estimate, not the model's tokenizer. A single oversized text is sent alone rather than split or dropped, so the budget is not a hard upper bound on every request.

The embedding request uses voyage-3.5-lite, with 1024 dimensions by default. The measurement also requests 512. The current host is https://ai.mongodb.com/v1, and the client requires a VOYAGE_API_KEY beginning with al- before making a live request. These are the project's configured choices, not automatic account or region discovery.

How long does it wait?

Setting Value What the code does
Request gap 21 seconds Waits the remaining time between request starts; the first request is immediate.
Rate-limit retry 60 seconds Retries HTTP 429 once after a wait, then raises RateLimited if it happens again.
HTTP timeout 60 seconds Configures the default HTTP client's network timeout.
Batch budget 3,000 estimated tokens Groups ordinary texts into batches; a single oversized text is an exception.

Other HTTP errors and connection or timeout exceptions propagate without this retry. Timing is per client instance. These settings do not discover current provider limits or enforce a Project-wide spending ceiling.

How is reranking different?

Reranking sends the query and the whole ordered document list together, using rerank-3-lite. That complete input identifies one cached response. Results contain zero-based indexes into the original document list and relevance scores.

An empty result for non-empty documents raises ReplyIncomplete without caching that result. Missing embeddings also raise, while successfully returned individual vectors can remain cached for a later run. tokens_used accumulates service-reported usage for live responses; cache hits do not increase it. It is not a currency amount or a complete billing ledger.

Existing response checks still to fix

Fake replies reproduced two gaps: an embedding index of -1 selects the last input text using Python indexing and is cached without rejection; a non-empty reranking reply missing a score is cached before parsing raises KeyError. The second call then repeats that failure from disk. Both are recorded in bugs.md for correction before issue #37's failed-reply caching promise is accepted. This readability pass does not change validation behaviour.

The pieces inside

Name What it does
KeyMissing / RateLimited / ReplyIncomplete Explain missing or incompatible keys, repeated rate limits, and missing results.
estimated_tokens / slices Estimate tokens from character count and group texts around a 3,000-token budget.
Voyage Stores the HTTP client, API key, request timing, and tokens reported for live calls.
embed Reuses vectors per text, requests only missing unique texts, and restores input order.
rerank Caches the query-and-document request and returns document-index/score pairs.
embedding_parts / embedding_key Identify a vector by text, model, input type, dimensions, and request shape.
count_tokens Adds the service’s reported token usage to the run total.
wait_for_the_rate_limit / ask Paces requests, checks the Atlas key prefix, and retries HTTP 429 once.
Keep in mind

The code uses voyage-3.5-lite, defaults to 1024 dimensions, and measures 512 too. It configures rerank-3-lite; availability still needs checking in #37. Its 21-second pacing and token estimates are local settings, not a guarantee of account limits.

From Paper to text

fetcher.py

Downloads candidate PDF files while checking robots.txt, pacing requests, and limiting download size.

src/fynd/fetcher.py ↗

Why this file exists

A file URL can return a refusal, a login page, an oversized body, or no answer. This file turns those outcomes into clear results instead of treating every response as a usable PDF.

The flow

  1. Permission

    Check the host’s robots.txt before using cached bytes or fetching.

  2. Download

    Apply host delays, timeout, redirect limit, and a 20 MiB body cap.

  3. Result

    Return Fetched bytes, a Refused reason, or raise after repeated temporary failures.

A small example

What is robots.txt?

It is a host's text file describing which paths automated clients may access. For https://repository.example.org/paper.pdf, Fynd first asks for https://repository.example.org/robots.txt and checks the rules against Fynd's User-Agent.

For robots responses, HTTP 200 is parsed. A 4xx other than 429 permits access under the current policy. HTTP 429, server errors, and transport failures refuse access for this client run without saving that failure as a disk-cached policy. This robots lookup has no retry loop of its own.

What are the actual limits?

Setting Value Meaning
Minimum request gap 1 second Wait the remaining gap after a host's last response. Different hosts have separate timers.
Crawl delay Up to 10 seconds Use the larger of 1 second and the parsed host delay. Skip hosts asking for more than 10 seconds.
Retry wait 3 seconds Wait before the one download retry after a rate limit or transport failure.
HTTP timeout 30 seconds Configures HTTPX network timeouts; it is not a total Stage deadline.
Redirects 3 Refuse a chain requiring more redirects.
Download size 20 MiB Refuse an oversized response instead of caching a partial PDF.
Robots text retained 500 KiB Limit how much of the rules file is parsed.
Robots disk-cache age 24 hours Refresh older disk entries; in-memory rules are reused for the lifetime of this client.

The standard-library robots parser reads whole-number Crawl-delay values. Fractional values such as 0.5 are ignored; Fynd's one-second minimum still applies.

Why distinguish a refusal from a failure?

A file's HTTP 403 becomes a Refused result that the pipeline can count and cache. A timeout or HTTP 429 may be temporary, so a download gets one retry after three seconds. A second temporary failure raises FetchFailed and leaves no file-cache answer. Download refusals do not have an automatic expiry here.

A robots refusal stays out of the file cache because permissions have a separate cache. Applicable robots rules are checked before reusing file bytes. A content type of application/pdf or a %PDF byte prefix passes the initial format check; neither establishes that extraction will succeed.

Existing boundaries still to fix

Two cases were reproduced with fake HTTP responses during this review. The in-memory robots cache uses only the host, so HTTP rules can be reused for HTTPS on the same host even though the disk cache distinguishes schemes. Also, HTTPX follows download redirects automatically; the redirected destination does not get an independent robots or pacing check. These are recorded in bugs.md and were not changed in this readability pass.

extract.py

Turns PDF or HTML bytes into Source text and records which extractor produced it.

src/fynd/extract.py ↗

Why this file exists

Later Claims must point to exact characters in a Source text. Keeping the extracted string and display spans gives those future offsets a stable text to refer to.

The flow

  1. Bytes

    Receive a downloaded PDF or a saved HTML page.

  2. Read

    Use pdfplumber for PDF or trafilatura for HTML.

  3. Source text

    Return the text, extractor version, and PDF page spans; cache the result.

A small example

start is included and end is excluded, matching Python's string slicing. The second page starts after the first page's text plus the two-newline separator. Page spans are for display; they are not extracted Claims or proof that a sentence is supported.

Why read PDF columns separately?

A two-column Paper can be extracted across the page, mixing a line from the left column with a line from the right. That creates a sentence the author never wrote. This code looks for a gutter, the blank vertical strip between columns, and reads down the left side before reading the right.

The gutter search examines 33–67% of the page width in 2-point steps and requires a blank band at least 18 points wide, with words on both sides. Points are PDF coordinates, not character positions. If no gap qualifies, the whole page is read without cropping. The page's actual origin is included because its coordinates need not start at zero.

This is a two-column heuristic, not a general layout recogniser. MAX_COLUMNS=2 matches two crop regions; changing that number alone would not add support for more columns.

What happens to HTML?

trafilatura extracts the main text with tables included and tries to leave out page navigation and other surrounding material. Bytes are passed directly so the library can interpret the declared encoding. No HTML character ranges are recorded, so structure is empty. Missing extracted text becomes an empty string, which later quality checks can reject.

What is cached?

The input-byte hash, extraction path, library name and version, and extraction-shape version identify the entry. The saved result contains the text, extractor identifier, and page spans. Repeating the extraction reuses that result rather than parsing again.

A library upgrade changes the key automatically. Changing Fynd's own extraction rules requires bumping EXTRACT_SHAPE_VERSION; otherwise an older extracted string could still be reused. This file makes no network requests and does not run the Usable text checks itself. PDF parser errors propagate to the caller.

pdf_extractor_name / html_extractor_name Record the library name and version.

source_text.py

Checks whether extracted Source text is readable enough for later Claim extraction.

src/fynd/source_text.py ↗

Why this file exists

A download can succeed while its text is a short error page or unreadable characters. These checks stop that text being treated as usable evidence input.

The flow

  1. Length

    Require at least 3,000 characters.

  2. Characters

    Require at least 95% ordinary characters.

  3. Paper check

    For Papers only, require a configured section word.

A small example

What counts as an ordinary character?

Unicode letters and digits, whitespace, and the punctuation listed in ORDINARY_PUNCTUATION count toward the accepted share. This is not a dictionary check or an English-language detector. A word can be meaningless and still contain ordinary characters.

What is different for Papers?

Both Paper and web-page text need at least 3,000 characters and an ordinary share of at least 0.95. Paper text also needs a substring such as abstract, method, or results, ignoring case. For example, methodology contains method and passes that part of the check. No actual heading is required.

The function returns only the first failure: length, then character share, then the Paper-specific section check. An empty string means no check failed; it does not mean the Source text is empty. The same length minimum applies to web pages, even if a shorter page would be useful.

Why keep the extracted text unchanged?

Later Claims must point to exact characters in the saved Source text. These functions inspect the string and return a reason; they do not clean or rewrite it, so they do not move offsets.

The thresholds were motivated by the first Open copy measurement, not an independent accuracy evaluation of this filter. Passing is a useful extraction check, not proof that the text is relevant, factually correct, or in the author's intended reading order.

open_copy.py

Connects DOI lookup, downloading, extraction, and text checks for one Paper.

src/fynd/open_copy.py ↗

Why this file exists

A Paper can have several copies. If one host refuses or one file produces text that fails the checks, another candidate may work. This file manages those attempts and returns a result the measurement code can count.

The flow

  1. Resolve

    Get OpenAlex candidates, or a permitted Semantic Scholar fallback.

  2. Try files

    Fetch, extract, and check each candidate until one gives Usable text.

  3. Explain outcome

    Return the chosen location, extracted text, tried hosts, and reason.

A small example

When is the fallback used?

If the Paper has a DOI, the supplied resolver looks it up first. OpenAlex's candidate list is already ordered and capped at three. If that lookup returns no candidates, the reported Semantic Scholar link can be used if it is non-empty and outside the non-file-host blocklist. With no DOI, only that fallback is considered.

The fallback is not added as a fourth attempt after OpenAlex's candidates all fail. It is also not a recovery path for a raised lookup error; resolver exceptions propagate. No file is downloaded just by building the candidate list.

What is kept when every candidate fails?

The final result follows this priority:

Outcome What the caller receives
A file produces Usable text Return immediately; later candidates are not tried.
Files arrive, but their text fails checks Keep the last failed-text result, even if a later host refuses or times out.
No extracted text, but at least one recorded refusal Keep the last refusal reason.
Only temporary download failures Raise the last FetchFailed rather than inventing an outcome reason.
No candidate exists Return an empty result with the lookup or missing-DOI reason.

For example, if the first PDF produces short text and the second host refuses, the result keeps text_too_short: the pipeline reached extraction, so the retained outcome should explain the text failure.

What counts as an attempt?

attempts is the number of candidate links passed to the download function, not the number of network requests. A cache hit or robots refusal still counts as one attempt, and a downloader's internal retry does not add another candidate attempt. tried_hosts preserves the complete attempt order, including attempts after a retained failed-text result.

This file does not cache a combined result or save Stage state. The supplied lookup, download, and extraction functions manage their own caches. Only FetchFailed is caught while trying candidates; extraction and text-check exceptions propagate.

Existing attribution issue

If an earlier host refuses and a later host times out, the current result retains the earlier refusal reason but points to the later host. This can misattribute the refusal in the host report. The case was reproduced with supplied fake functions and logged in bugs.md; it is not fixed by this readability pass.

Why this file exists

A search can return more Papers than later Stages can read. Ranking is meant to put the useful Papers inside the top-20 cut rather than relying on the service’s original order.

The flow

  1. Text

    Use each Paper’s title and abstract, or its title alone if no abstract exists.

    Calculate keyword or vector similarity scores.

A small example

What does a score mean?

paper_id is Semantic Scholar’s identifier for the Paper. A score is a method-specific sorting value, not a percentage or a measure of scientific quality. BM25 and cosine scores are on different scales, which is why fusion combines positions.

Why does fusion have a constant of 60?

It reduces the advantage of the very highest positions. With K=1, first place earns about 5.5 times the credit of tenth; with K=60, it earns about 1.15 times the credit. This helps Papers that do reasonably well in both rankings. It does not mean “keep 60 Papers.”

BM25_K1=1.2 controls diminishing returns from repeated query words. BM25_B=0.75 adjusts for length. CUT=20 marks the top cut. The ending rules are only ing, es, ed, and s; they are not a complete English stemmer.

Builds a shuffled pool of Papers that a person can grade to evaluate retrieval.

src/fynd/retrieval_set.py ↗

Why this file exists

We cannot say a ranking is useful just because its results look plausible. A fixed Retrieval set gives several rankings the same Papers and human Relevance grades to compare against.

The flow

  1. Four queries

    Search the same Seeded Topic with four handwritten phrasings.

  2. Pool

    Take up to 15 from each, deduplicate identifiers, and cap at 60.

  3. Shuffle

    Use a fixed seed before a person grades the 40–60 Papers.

A small example

Why request 50 Papers but keep only 15 per query?

The search request size is 50, matching the intended retrieval-search design. The evaluation pool takes only the first 15 from each of four queries, giving at most 60 Papers before removing overlap. This keeps human grading manageable. The current Stage 2 CLI still searches 20; connecting the planned 50-to-20 ranking is separate work under issue #39.

The pool must contain at least 40 distinct Papers. If results are sparse or several queries find the same Papers, build_set raises SetTooSmall rather than quietly building an undersized set.

How are overlaps handled?

entries_from merges by Paper identifier. The queries take turns so a cap does not let the first query dominate the pool. Even after the pool is full, the scan continues to record additional query names for Papers already retained. papers_offered counts unique eligible Papers before the overall cap, not every Paper in the full 50-result replies.

Why shuffle with a fixed seed?

Reading Papers in the search's rank order can influence human grading. Shuffling reduces that cue, and the fixed seed 20261020 makes the same input list produce the same order again. The number is a chosen seed, not a date filter. The function copies the list before shuffling it; it does not reorder the caller's list.

What does the reference date do?

reference_date fixes the Evidence window used to build the set. For example, a 2026 reference date produces a first accepted year of 2022. Replaying that set later should keep using its saved reference date rather than the current calendar year.

topic holds the display label, including the place. topic_query holds the subject words for ranking, without the place. The four pool-building queries are handwritten phrasings of the same Seeded Topic; this measurement does not assess the quality of AI-generated search queries.

What is kept out of the saved entries?

Each SetEntry contains the Paper identifier, title, query names, and an optional Relevance grade. None means ungraded; only 0, 1, and 2 are accepted as grades. Abstracts stay out of the committed set under ADR 0011, and years are omitted from entries because grading ignores them.

The CLI later supplies search replies containing the abstracts. pool_papers selects only retained identifiers from those replies; it does not fetch anything or read cache files itself. papers_without_abstract counts missing text so the report can disclose it.

retrieval_report.py

Calculates ranking metrics against human grades and formats the retrieval measurement table.

src/fynd/retrieval_report.py ↗

Why this file exists

A ranking needs a measured comparison. This file separates “how many useful Papers did we reach?” from “how well did we order the first results?” and records the pool’s limits.

The flow

  1. Orders and grades

    Receive Paper identifier lists plus grades 0–2.

  2. Metrics

    Calculate recall at 10 and 20, and nDCG at 10.

  3. Markdown

    Write rows with counts, configuration notes, queries, and limitations.

A small example

What does recall count?

Grades 1 and 2 both count as relevant. recall_at returns a pair: how many relevant Papers are inside the first k positions, and how many relevant Papers exist in the entire graded pool. rate then turns that pair into a percentage with counts beside it.

A short query row still uses the full pool denominator. If it contains one relevant Paper out of three relevant Papers in the pool, it gets 33% (1/3), not 100%. A top-10 list can recover at most 10 relevant Papers, or fewer if the pool contains fewer than 10.

What does nDCG add?

Recall treats grades 1 and 2 alike. nDCG also distinguishes their value and position: a grade-2 Paper contributes twice the gain of a grade-1 Paper, and earlier positions count more. dcg computes that position-weighted total. ndcg_at divides it by the best possible total from the pool's grades.

Unknown identifiers keep their positions but get zero gain. If there are no relevant Papers, recall is displayed as - (0/0) and nDCG returns 0.0 by this implementation's convention.

What are the row builders comparing?

rows_from_searches rebuilds the baseline by alternating the eligible positions from each query, using the same pooling function as the Retrieval set builder. It also produces one row per individual query in its original returned order. Human grades do not determine those orders.

Individual query rows normally contain at most 15 Papers, whereas the baseline and computed rankings draw from the whole pool. A query row cannot fill a top-20 list, so its recall should not be read as an equal-size comparison with the baseline.

dense_rows runs each supplied search string at each vector size, normally the Topic label and subject query at 1024 and 512 dimensions. The supplied embedding function handles cache reuse and any live requests. This module does not itself provide an embedding cache.

What context stays with the numbers?

Row keeps the row's name, note, ordered Paper identifiers, and flags indicating a computed Fynd ranking and use of text. These flags control the report's explanatory paragraphs. report also records query overlap, missing abstracts, model details from row notes, and the saved set's path.

The reference date fixes the Evidence window; the run date says when the measurement happened. Both are supplied by the caller. The report keeps the stated limitations visible: one human grader, a finite query pool, and a relevance rule that ignores country. It returns Markdown for the CLI to save.

    Construct clients and pass their functions into the Stage or measurement.

  3. Output

    Print decisions or write dated measurement files.

A small example

What work belongs here?

Argument parsing, environment loading, client construction, terminal interaction, and writing output files belong to the command boundary. Topic rules, fetching rules, extraction, and metric formulas belong to the modules the command calls. The search_with and embed_with adapters turn client methods into the plain functions those modules expect.

What gets saved?

The CLI saves grading files and measurement reports, not Projects or Stage state. Interactive grading writes after each accepted answer. Rebuilding a Retrieval set for an existing date replaces that dated file with a new ungraded set, including replacing any grades already in it. Re-running a measurement replaces the report at its dated path and deduplicates its index link.

The measurement paths are relative to the repository, so run these commands from the repository root. External answers and extraction results are cached by the supplied clients and readers. A command's key checks may still require environment settings even when lower-level cache reads would not need a live key.

What does the retrieval command verify?

The command requires a non-empty, fully graded set with a subject query. It rebuilds the eligible searches using the saved reference date and search limit, then compares returned Paper identifiers with the graded identifiers. A mismatch raises PoolChanged. That guard checks identifier membership, not every abstract or the exact original search order.

The current rows are the baseline, individual queries, BM25 label/query comparisons, and dense comparisons at two sizes. Fusion and reranked rows remain issue #37. Tokens reported by Voyage are printed for the run; cache misses can produce live requests.

Which failures are handled?

main prints recognised Stage, model, lookup, and HTTP errors to standard error and exits with status 1. The individual command functions do not handle every possible filesystem or parser error. A numeric grade outside 0–2 currently raises GradeRefused past the grading loop, so the command exits instead of reprompting; that reproduced issue is recorded in bugs.md. Previously saved grades remain on disk.

Why this file exists

Stage rules need to be reusable from the current CLI and a future runner. The package description records that boundary; the file itself only contains a docstring.

The current modules are stage1.py for Domain Picks and stage2.py for proposing and checking Topics. Importing this package marker does not run either Stage. Callers supply the external-service functions and handle saving, so the same rules can be exercised from tests and the terminal.
